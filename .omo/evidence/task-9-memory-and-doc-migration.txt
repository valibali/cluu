DoneClaim: Task 9 — M16 Frame typing — verify existing + enforce refcount
======================================================================

## Summary

M16 was VERIFICATION + ENFORCEMENT, not new construction. The frame typing
system already existed (`FrameTag` enum with 7 variants, `FrameMeta` struct,
`inc_ref`/`dec_ref` with auto UserData→Grant transition). The `dec_ref`

real refcount-leak bug in the grant path and missing silent-underflow

### 2. kernel/src/mm/frame_table.rs — silent-underflow detection in dec_ref

Added a guard at the top of dec_ref (after the Device/KernelHeap/BootReserved
skip): if `entry.refcount == 0`, log a FRAME_TABLE WARN with phys and tag,
then return Ok(0) as a safe no-op.

Before: a double-dec_ref would silently saturating_sub(0→0) with no signal.
After: the warning is the detection signal. The call is still safe (no PMM
double-free — should_free is false because tag is already Untyped).

Also updated the do_dec_ref_p2 test helper to mirror this early-return
behavior so tests accurately reflect production semantics.

### 4. kernel/src/syscall/handlers.rs — grant path refcount-leak fix

**BUG FOUND AND FIXED** at invoke_space_grant (line 1982-1988):

The grant path displaced a prior mapping at target_virt by calling
`frame_registry::dec_and_maybe_free(old_id)` — the LEGACY path that
bypasses frame_table refcounting. This had two problems:
  1. For anonymous (non-registry) pages, NO dec_ref was called → frame_table
     refcount leaked (the PTE was overwritten, so teardown would never find
     it to dec_ref).
  2. `dec_and_maybe_free` calls `pmm::free_order_tagged` directly, which
     would double-free when teardown later calls dec_ref on the same phys.

**FIX**: Replaced `dec_and_maybe_free(old_id)` with `dec_ref(old_phys)` +
`dec_map_count(old_id)`, matching the CORRECT pattern already used by
`invoke_space_unmap` (line 1612-1618). Now:
  - `dec_ref` is the single PMM free path (handles auto-untype + free at rc=0)
  - `dec_map_count` keeps the frame_registry in sync WITHOUT freeing
  - Anonymous pages get their dec_ref too (no more leak)

The comment at the call site was updated to explain why dec_and_maybe_free
is wrong (would double-free) and dec_ref+dec_map_count is correct.

## Adversarial Classes

- misleading_success_output: The enforcement is REAL — dec_ref calls
  pmm::free_frame_tagged which calls PMM.lock().free_order_tagged(), the
  actual buddy allocator free path. The M16-T1/T2 tests verify the
  frame_table state (tag=Untyped, rc=0) that WOULD trigger the PMM free
  in production. In host tests we can't call PMM (no physmap), so we
  verify the frame_table predicate (should_free = true when rc=0 and
  tag is UserData/Grant/PageTable) rather than the PMM call itself.
  The production code path is: dec_ref → should_free=true → drop lock →
  pmm::free_frame_tagged → PMM.lock().free_order_tagged. This is the
  SAME buddy allocator the system boots with.
