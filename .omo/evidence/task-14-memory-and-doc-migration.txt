CHANGE 1: memory.rs — MAP_SHARED | MAP_ANONYMOUS wrapper
============================================================
Added a new branch in _mmap() (after the existing fb0 file-backed
MAP_SHARED path, before the generic anonymous/file-backed handling).

The branch triggers when:
  is_anonymous == true  AND  (flags & MAP_SHARED) != 0  AND  offset != 0

Behavior:
  - Treats `offset` as a source virtual address in the caller's own
    space (CLUU-specific extension; POSIX offset is undefined for
    MAP_ANONYMOUS).
  - Validates offset is page-aligned (EINVAL if not).
  - Routes to space_map_range with MAP_SHARE_PHYS flag, passing:
      space_token = caller's own space token (crate::boot::space_token())
      virt_addr   = new VA in mmap region (first-fit or MAP_FIXED)
      src_virt    = offset (source VA in caller's space)
      kern_flags  = PROT_READ|PROT_EXEC (PROT_WRITE dropped) | MAP_SHARE_PHYS
      num_pages   = aligned_len / PAGE_SIZE
      data_len    = aligned_len (must be non-zero per kernel validation;
                    kernel does not copy data for MAP_SHARE_PHYS)
  - The kernel remaps the caller's physical frames backing src_virt
    into the caller's own space at virt_addr, always read-only.
  - Tracks the region in MMAP_REGIONS for munmap/mprotect bookkeeping.
  - Stores effective_prot = prot & !PROT_WRITE (reflects actual
    read-only mapping).

MAP_SHARED | MAP_ANONYMOUS with offset == 0 falls through to the
existing anonymous zero-fill path (same as MAP_PRIVATE | MAP_ANONYMOUS).
The caller can later share that region cross-process via
space_map_range with the receiver's space token + MAP_SHARE_PHYS.

Cross-process sharing: mmap only holds the caller's own space token,
so the cross-process step (mapping into another process's space) uses
space_map_range directly with the receiver's token. This is documented
in doc/book/memory_model.md.

Lines added: ~100 (including comments explaining the non-obvious
offset-as-source-VA convention, the kernel's silent PROT_WRITE drop,
and the data_len non-zero requirement).

RESIDUAL RISK
============================================================
1. The MAP_SHARED wrapper uses the caller's own space token, so it only
   creates same-space read-only aliases. Cross-process sharing requires
   the caller to hold the receiver's space token and call space_map_range
   directly. This is documented but not wrapped in a convenience
   function — per the plan, this is "documentation + wrapper, not new
   IPC."

2. The `offset` parameter is repurposed from POSIX file-offset to source
   virtual address for MAP_SHARED|MAP_ANONYMOUS. This is a CLUU-specific
   extension, documented in the code comments and in memory_model.md.
   Callers passing a non-zero offset to MAP_SHARED|MAP_ANONYMOUS will
   get the MAP_SHARE_PHYS path rather than undefined behavior.

3. memory_model.md and ipc.md not yet in doc/src/lib.rs (todo 23). The
   content is correct and will render once todo 23 registers the modules.

4. Pre-existing host-test failure (process.rs IpcFlags import) blocks
   `cargo test --features host-test` for the entire libcluu crate. Not
   caused by this task; not in scope to fix.
