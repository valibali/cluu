CHANGES
-------

1. kernel/src/architecture/x86_64/idt.rs — refactored handle_heap_fault:
   - handle_heap_fault is now a dispatcher: routes stack-region faults to
     handle_stack_fault, heap-region faults to demand_map_page.
   - handle_stack_fault (NEW): calls warn_stack_growth_threshold, then
     demand_map_page. Stack pages mapped read+write+no-exec (executable=false
     in map_user_page → NX bit set in PTE).
   - warn_stack_growth_threshold (NEW): fires one-shot [WARN] when stack
     growth crosses 1 MB, 4 MB, 8 MB thresholds. Algorithm: each threshold
     boundary (USER_STACK_TOP - N*MB) lives in exactly one 4 KB page; fire
     when that page is demand-faulted. Deduplicates naturally, no per-process
     state, IRQ-safe, no allocation.
   - demand_map_page (NEW): shared frame-alloc + map logic extracted from
     the old handle_heap_fault. Maps with writable=true, executable=false
     (NX set for both stack AND heap). Owner lookup tags PT frames correctly.
   - 16 MB hard limit enforced structurally: guard page at USER_STACK_BOTTOM
     (0x7f000000) is never demand-paged (excluded from stack_guard_end..TOP
     range check), so overflow kills the thread.

2. kernel/src/mm/fault.rs — FaultHandler::handle routing update:
   - Added stack fault check before heap check: if space.stack.contains(addr)
     and not a protection violation, route to handle_lazy_stack.
   - handle_lazy_stack (NEW): allocates a frame, maps with PageFlags
     {writable: true, no_execute: true} (read+write+no-exec).
   - Null-region AddressSpace::new initializes stack to a zero-size region
     (contains() returns false for all addresses), so existing tests are
     unaffected.

3. userspace/probes/stackgrow/ (NEW) — test probe:
   - Cargo.toml, src/main.rs
   - Mode "grow" (default): touches N pages going down from USER_STACK_TOP
     (0x80000000), verifying demand paging. Default depth=1000.
   - Mode "overflow": touches 5000 pages (~20MB > 16MB limit) to verify
     thread kill by guard page.
   - Registered in workspace Cargo.toml + containers/stackgrow/Cluufile.

4. Cargo.toml — workspace registration:
   - Added "userspace/probes/stackgrow" to members list.
   - Added [profile.dev.package."cluu-stackgrow"] and
     [profile.release.package."cluu-stackgrow"] with debug=0.

5. containers/stackgrow/Cluufile (NEW):
   - FROM minimal, PROFILE ipc vfs registry, ENTRYPOINT /bin/stackgrow.

KNOWN ISSUES (out of scope)
===========================

1. Process stack address mismatch: actual process stacks are at
   PROC_STACK_BASE=0x6f000000 (wiring.rs:55, 64 KB), but the kernel's
   demand-pageable stack region is USER_STACK_BOTTOM..USER_STACK_TOP =
   0x7f000000..0x80000000 (space.rs:52-54, 16 MB). These are DIFFERENT
   regions. The 64 KB process stack at 0x6f000000 has a MAP_GUARD page
   below it and does NOT benefit from demand-paged growth. To make real
   process stack growth work, wiring.rs would need to place stacks in the
   0x7f000000 region (out of scope — wiring.rs is read-only).

2. Probe crash at 0x7fe00000: the stackgrow probe crashes with a protection
   violation (error code 0x7 = present + write + user) when writing to
   0x7fe00000 (PD[0xFF], PT[0] in the stack region). This is a pre-existing
   page-table aliasing issue (PT[0] is present but not writable, likely
   from frame reuse in map_user_page). The probe successfully demand-pages
   512 pages (2 MB) before hitting this. Not caused by M10 changes.

3. OVMF NVRAM issue: after the first QEMU boot, subsequent boots with fresh
   OVMF copies drop to the UEFI shell instead of booting CLUU. This is a
   test infrastructure issue (OVMF NVRAM boot order), not a code issue.
   Workaround: use the same OVMF.fd file across runs, or use pflash with
   separate code/vars files.
