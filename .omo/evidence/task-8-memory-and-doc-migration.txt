Summary
-------
Added InvokeOp::MemoryPressure (variant 87) — a coarse-grained
cache-release signal. procmgr invokes it on a target process's
registered pressure-notification token; the kernel ORs bit
`(1 << level)` into the notification's pending word, waking the
target which releases caches. Combined with the existing OOM
callback (C4, allocator.rs:689-744), this gives the two-tier
memory-response ladder:

  tier 1 (pressure) → release caches   (this task, M7)
  tier 2 (OOM)      → run GC            (C4, done)

New InvokeOp variant number: 87 (next after ThreadSetSystemScope=86).

Plan-inaccuracy note
--------------------
The plan said libcluu has a `from_usize` match arm to update.
libcluu's InvokeOp enum has NO `from_usize` method — only the
kernel enum does. Dual-enum sync is enforced via:
  (a) matching discriminant value (87) on both sides, and
  (b) libcluu's `test_invoke_ops` which asserts
      `InvokeOp::MemoryPressure as usize == 87`.
Adding a `from_usize` to libcluu would have been scope creep
(new infrastructure not present in the existing code).

Handler signature
-----------------
fn invoke_memory_pressure(
    token: &Token,
    obj_ref: ObjectRef,
    args: SyscallArgs,
) -> SyscallResult

  - token:    caller's notification token (must have WRITE right)
  - obj_ref:  ObjectRef::Notification(id) resolved from token
  - args.arg3: pressure level (0..63); kernel shifts to bit (1 << level)
  - returns:  Ok(0) on success; Err(PermissionDenied) if no WRITE right;
              Err(InvalidArgument) if wrong object type or level >= 64.

API contract
------------
- arg3 = pressure level (coarse): 0=soft, 1=hard, 2=critical.
  Caller passes the level; kernel does the bit shift. Kernel is
  the single source of truth for the bit encoding.
- No-op if no waiter is registered (bits accumulate in the
  notification's pending word until consumed via notification_wait).
- No per-page pressure tracking (per MUST NOT DO).
