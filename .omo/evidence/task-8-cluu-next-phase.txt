===================================================

== Summary ==

The netd service was already on disk from a previous agent's work. I reviewed
the implementation, found and fixed 3 bugs, added netd to the INIT_CRATES
build list (was missing), and verified the service boots correctly with the
smoltcp interface initialized.

== Bugs Found and Fixed ==

### Bug 1: netd get_mac reads MAC from wrong offset (netd/src/main.rs)

The `get_mac` function used `call_with_reply_buf` to query the virtio-net
driver for the MAC address. The reply buffer layout is:
  [Message header (56 bytes) | payload (6-byte MAC)]

The old code read `reply_buf[0..6]` (the Message header bytes, not the MAC).
This produced MAC `03:04:00:00:02:00` (the label+tag bytes) instead of the
real MAC `52:54:00:12:34:56`.

Fix: Read from `reply_buf[size_of::<Message>()..]` (the payload section).

### Bug 2: virtio-net doesn't handle async IPC replies (virtio-net/src/main.rs)

netd sends TX frames to virtio-net via `IpcCallFuture` (async runtime, per
AGENTS.md §7). `IpcCallFuture` sets `tag.extra = ASYNC_REPLY_TAG` on the
request message. The virtio-net driver used `extract_reply_id(msg)` which
returns `None` for `ASYNC_REPLY_TAG` messages (it only handles
`REPLY_ID_TAG`). Result: no reply was sent, and the `IpcCallFuture` task
hung forever waiting for a reply that never came.

Fix: Replaced `extract_reply_id` + `reply`/`reply_with_payload` with
`reply_to_sender`/`reply_to_sender_with_payload`, which handle both sync
(`REPLY_ID_TAG` → `ipc_reply`) and async (`ASYNC_REPLY_TAG` → `ipc_send`
to reply endpoint with cookie) reply paths.

### Bug 3: virtio-net uses ipc_reply for frame notifications (virtio-net/src/main.rs)

The `drain_rx` function sent received frames to netd's registered endpoint
using `reply_with_payload(self.recv_endpoint, ...)` which calls `ipc_reply`.
But `ipc_reply` only works for pending `ipc_call` reply routing — it cannot
send to an arbitrary endpoint. The kernel's `sys_reply` handler looks up
`take_call_reply_info_verified(reply_id, current)` and returns
`Err(PermissionDenied)` if no pending call matches. Frame notifications
were silently dropped.

Fix: Replaced `reply_with_payload` with `send_msg_with_payload` (which uses
`ipc_send` — correct for sending to an endpoint).

### Bug 4: netd missing from INIT_CRATES build list (xtask/src/main.rs)

netd was in `sys_programs` (for initrd copy) but NOT in `INIT_CRATES` (for
building). The binary in the initrd was stale from a previous manual build.
Added "netd" to the `INIT_CRATES` array.

== Release Profile Note ==

The release profile (`opt-level = "z"`, `lto = true`, `panic = "abort"`)
causes a pre-existing kernel page fault at RIP 0xffffffffffe022be
(`mov 0x80(%r10), %rsi` where r10=0x11, fault address=0x91). This crash
occurs AFTER all services are launched, in the kernel's scheduler/IPC
dispatch path. It is NOT caused by netd or virtio-net changes — it
reproduces with the kernel changes stashed (original kernel code) and
with netd removed from the boot sequence. The crash is a latent kernel
bug exposed by the aggressive size optimization + LTO. Dev profile
(opt-level=0, no LTO) works correctly.

== Implementation Review ==

The netd implementation (userspace/netd/src/main.rs, 522 lines) was
reviewed against the task requirements:

  [x] Uses async runtime (Runtime, IpcCallFuture) — NOT blocking IPC
      - TX frames sent via IpcCallFuture in drain_tx()
      - Runtime poll_ready() + pop_completion() in main loop
      - Reply endpoint in ipc_recv_any_with_sender tokens
  [x] Has smoltcp Interface poll loop
      - iface.poll(now, &mut device, &mut sockets) each iteration
  [x] Has IPC label dispatch for all socket operations
      - NET_SOCKET: creates TCP/UDP/ICMP/raw sockets via smoltcp
      - NET_CLOSE: removes socket from SocketSet
      - NET_BIND/CONNECT/LISTEN/ACCEPT/SEND/RECV/POLL: stubbed (-78 ENOSYS)
  [x] Bridges to virtio-net via IPC for frame I/O
      - Registers recv endpoint via NET_REGISTER_RECV
      - Receives frames on pkt_recv_ep, pushes to device.rx_queue
      - Sends frames via NET_PKT_SEND through IpcCallFuture
  [x] No unwrap() in non-test code
  [x] No panic in non-test code
  [x] No blocking IPC in main recv loop (get_mac and NET_REGISTER_RECV
      use blocking call() during initialization, before the main loop)
  [x] No DHCP/ARP/ICMP implementation (that's todo 9)
  [x] No socket API library (that's todo 10)
  [x] No new syscalls (uses IPC message labels)
  [x] no_std + alloc, Result<T> over panics
