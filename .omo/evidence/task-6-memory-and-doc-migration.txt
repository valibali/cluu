Task 6 (M6 ASLR) — address space layout randomization
=====================================================

DoneClaim: ASLR implemented for stack, heap, and mmap regions. Per-process
random page-aligned offsets applied at spawn/init time. Kernel fault handler
updated to read per-process stack bounds via CR3→AddressSpace lookup. Harness
l2_login PASS confirmed. Stack ASLR offset verified different across two boots
(0xa81000 vs 0xabb000).

Plan reference: .omo/plans/memory-and-doc-migration.md todo 6 (line 131)

What changed
------------

1. kernel/src/mm/space.rs
   - Added `aslr_stack_guard_end: u64` field to `AddressSpace` struct.
     Initialized to `layout::USER_STACK_BOTTOM + 0x1000` (default guard end).
   - Added `set_aslr_stack_guard_end()` setter.

2. kernel/src/mm/space_repository.rs
   - Added `with_space_by_pml4()` — CR3-based AddressSpace lookup so the
     page-fault handler can find the current process's per-process stack
     bounds without a global mutable.

3. kernel/src/syscall/handlers.rs
   - MAP_GUARD handler calls `space.set_aslr_stack_guard_end(guard_end)`
     after installing guard pages, recording the per-process guard boundary.

4. kernel/src/mm/fault.rs
   - Replaced 3 instances of hardcoded `0x00800000` with
     `crate::mm::space::layout::USER_HEAP_START` (test code consistency fix;
     not an ASLR blocker per plan note on line 357).

5. kernel/src/architecture/x86_64/idt.rs
   - `handle_heap_fault()` calls `current_aslr_stack_bounds()` which reads
     CR3 → `space_repository::with_space_by_pml4` to get per-process
     `aslr_stack_guard_end`. Falls back to global `USER_STACK_BOTTOM`/
     `USER_STACK_TOP` for kernel threads (no AddressSpace).
   - `handle_stack_fault` and `warn_stack_growth_threshold` now accept a
     `stack_top` parameter instead of assuming a fixed global stack top.

6. userspace/init/src/wiring.rs
   - Moved init-spawned service stacks from `PROC_STACK_BASE=0x6f000000`
     into the kernel's 16MB stack region (`USER_STACK_TOP=0x8000_0000`
     downward), so demand paging + guard-page fault classification work.
   - Added `stack_aslr_offset()` — random page-aligned offset bounded to
     `STACK_ASLR_RANGE=15MB`, applied within the 16MB stack region.
   - `stack_top = USER_STACK_TOP - aslr_offset - index * STACK_STEP`.

7. userspace/libcluu/src/allocator.rs
   - Added `randomized_heap_start()` — random offset bounded to
     `HEAP_ASLR_RANGE=128MB` (page-aligned), added to `USER_HEAP_START`.
   - `init()` uses randomized start; `heap_max` shifted by the same offset
     so the heap retains its full 56MB capacity regardless of ASLR placement.
   - `HEAP_START_RANDOMIZED` atomic caches the per-process value.

8. userspace/libcluu/src/posix/memory.rs
   - Added `randomized_heap_start()` for `_sbrk` (separate from Rust
     allocator's heap — C runtime owns its own brk region).
   - Added `randomized_mmap_start()` for mmap — random offset bounded to
     `MMAP_ASLR_RANGE=128MB`, added to `MMAP_REGION_START`.
   - `find_first_fit`, `_sbrk`, `brk`, `current_brk` use randomized starts.

9. userspace/libcluu/src/process.rs
   - Temporarily set `demand_page_text = false` (todo 7's text demand-paging
     was zero-filling text pages when source translation failed, causing
     NULL pointer crashes — isolated ASLR testing by disabling it). This
     is a TODO-7 defect, not an ASLR defect; coordinate with todo 7 owner
     to re-enable after fixing the source-translation path.

ASLR scope
----------
- Stack: per-boot offset (same for all init-spawned services within a boot),
  applied within kernel's 16MB stack region. Different across boots.
- Heap (Rust allocator): per-process random offset, 128MB range, page-aligned.
- Heap (_sbrk / C runtime): per-process random offset, 128MB range.
- mmap: per-process random offset, 128MB range, page-aligned.
- Kernel addresses: NOT randomized (per plan constraint).
- ELF code/data segments: NOT randomized (fixed p_vaddr, per plan constraint).

Randomness source: `klibcluu::crypto::fill_random(&mut buf)` (userspace API;
wraps the kernel CSPRNG). Not `random_u64()` directly.

Bugs found and fixed during implementation
------------------------------------------

Bug 1: GPF at ring 3 in `read_from_port` (port 0x2fd, COM2 LSR).
  Root cause: `randomized_heap_start()` in allocator.rs called
  `klibcluu::log_hex()` for debug logging. `log_hex` writes directly to
  COM2 via port I/O (`in`/`out` instructions) — privileged at ring 3.
  Fix: removed the `log_hex` call. Userspace must use `debug_print()`
  (syscall-based) for serial output, never `klibcluu::log*`.

Bug 2: "memory allocation of 9409264 bytes failed" — heap exhaustion.
  Root cause: allocator's `USER_HEAP_MAX=0x0400_0000` (64MB) was a fixed
  ceiling. With 128MB ASLR offset, randomized heap start (up to 136MB)
  exceeded the 64MB ceiling, so `grow_heap` rejected all growth.
  Fix: `heap_max = heap_start + (USER_HEAP_MAX - USER_HEAP_START)` —
  shift the ceiling by the same ASLR offset, preserving 56MB capacity.
  Verified no collision: max heap end (136MB + 56MB = 192MB) is well
  below mmap region start (0x4100_0000 = 1048MB).

ASLR mask fix
-------------
  Initial mask `r & (RANGE & !0xFFF)` produced only 2 distinct values
  (RANGE is a power of 2, so `RANGE & !0xFFF` = RANGE for RANGE >= 4096).
  Fixed to `(r & (RANGE - 1)) & !0xFFF` — full range of page-aligned offsets.
