# Plan: Per-File Documentation Headers for CLUU Source

**Status:** Draft, awaiting Momus review
**Owner:** Sisyphus
**Created:** 2026-07-06
**Scope decision (locked with user):** Kernel + libcluu + core services only. Skip probes, tests/kernel, xtask, tiny POSIX utils.
**Visuals decision (locked with user, 2026-07-06):** Add FB-dump screenshots and GIF animations where they illustrate behavior; embed by reference in file/module headers.

---

## 1. Goal

Add a standardized, structured documentation header to the top of every
in-scope Rust source file. Each header must, in this order:

1. State what the file is for (its role in CLUU).
2. State what the file implements (concrete types, traits, functions,
   responsibilities — grounded in the actual code, not aspirational).
3. State how that implementation serves CLUU's architecture: which
   AGENTS.md premises it embodies (§2 caps, §3 no runtime ACL, §4
   encapsulation-at-spawn, §5 session, §6 root godmode, §7 async
   runtime), which design drivers force its shape, what invariants
   must hold.
4. Cross-reference related files, IPC op labels, premises, and
   `docs/ARCHITECTURE.md` / `docs/INTERNALS.md` sections.

The deliverable is the input material for a later, separate milestone:
a comprehensive CLUU documentation suite generated by harvesting these
headers. Headers must therefore be mechanically harvestable (fixed
section anchors) and individually truthful.

## 3. Header Template

Every in-scope file gets a header block immediately after the
inner-attribute block (`#![...]`) and before any `extern crate` or
`use` statements. The header is `//!` (module-level) doc comments.

### 3.1 Standard template

```rust
//! # {Short file title — human readable, e.g. "Capability Token Table"}
//!
//! {One-sentence role statement. What problem this file solves, in CLUU terms.}
//!
//! ## Role in CLUU
//!
//! {1-2 paragraphs. Where this file sits in the crate and in the
//! overall system. Who calls it, what it is called by, what it
//! depends on. For services: which IPC endpoint it owns, which
//! `InvokeOp`s it dispatches. For kernel subsystems: which syscall
//! surface it underpins.}
//!
//! ## What it implements
//!
//! {Concrete enumeration of the public/named symbols defined in this
//! file: types, traits, functions, constants. Group by responsibility
//! if the file is large. Use the actual symbol names — do not
//! paraphrase. For very large files (>1500 LOC) break this into
//! sub-sections by responsibility.}
//!
//! ## Design drivers & invariants
//!
//! {Why the code is shaped this way. Which AGENTS.md premises apply
//! (cite §2/§3/§4/§5/§6/§7 explicitly). What invariants the code
//! relies on and what it preserves. Any deadlock-avoidance,
//! race-avoidance, or capability-discipline reasoning. If the file
//! implements a pattern documented in `docs/INTERNALS.md` or
//! `docs/PROCESS_ISOLATION_DESIGN.md`, point at it.}
//!
//! ## Cross-references
//!
//! - Related files: `path/to/file.rs` — {why related}
//! - IPC ops / labels: {e.g. `VFS_SET_VIEW_LABEL`, `InvokeOp::ThreadCreate`}
//! - AGENTS.md: §{N} {short reason}
//! - docs/ARCHITECTURE.md: §{N} {short reason}
//! - docs/INTERNALS.md: §{section} (if applicable)
```

### 3.2 Template rules

- **Section anchors are fixed.** Every header has exactly the five
  sections above (title, Role, What it implements, Design drivers,
  Cross-references). A section may be one line if the file is trivial,
  but the heading must be present. This is what makes the later
  harvest mechanical.
- **Grounding is non-negotiable.** Every claim about what the file
  implements must be verifiable by reading the file. Symbol names must
  match exactly. If a function was removed, do not list it. If a
  behavior is aspirational, do not claim it.
- **Premises cited must apply.** Do not cite §3 (no runtime ACL) for a
  file that does not touch authorization. Cite only the premises the
  file actually embodies.
- **Cross-references must point at real things.** File paths must
  exist. IPC labels must exist in `userspace/libcluu/src/ipc.rs` or the
  relevant op registry. §N must match AGENTS.md or docs/ARCHITECTURE.md.
- **No praise, no filler.** State what and why. Do not write "this
  module provides a clean abstraction" or "elegantly handles".
- **Length scales with the file.** A 50-line file gets a ~20-line
  header. A 5000-line file gets a ~150-line header with sub-sections.
- **Preserve accurate technical content from existing headers.** If
  the existing `//!` block says something true and specific, fold it
  into the right section. Do not lose information.

### 3.3 Visual asset references in headers

File headers may reference screenshots/GIFs that illustrate the
file's runtime behavior. References are relative paths under
`docs/assets/` and use Markdown image syntax inside the `//!`
block:

```rust
//! ## Cross-references
//!
//! - Runtime behavior: `docs/assets/tty-line-discipline.gif`
//!   (canonical/obvious Ctrl-C, backspace, ↑ history, line echo)
```

**Rules:**

- **Visuals are optional per file.** Add them only where the file's
  behavior is *visible* and a picture materially helps. Internal
  modules (kernel, libcluu, procmgr, vfs, ext2, virtio-*) get no
  visuals by default. Visuals land in: console, compositor, vtmgr,
  tty, cluuterm, shell, edit, init (boot), and any other crate with
  a user-visible surface.
- **No binary blobs in source.** A header references an asset by
  path; the asset lives under `docs/assets/`. Never inline image
  data.
- **Asset naming:** `docs/assets/<crate>-<behavior>.{png,gif}`.
  Examples: `vtmgr-vt-switch.gif`, `console-boot-to-login.gif`,
  `shell-command-history.gif`, `tty-line-discipline.gif`.
- **Caption is one line in the header.** The asset file's own
  companion `.md` (e.g. `docs/assets/vtmgr-vt-switch.gif.md`) holds
  the long caption, capture conditions (QEMU args, resolution, what
  to look at), and a transcript of the keystrokes that produced it.
  This keeps the source header terse and the asset self-documenting.

### 3.4 Worked example (real file, illustrative header)

For `userspace/libcluu/src/registry.rs` (current first 7 lines
paraphrased into the new template):

```rust
//! # Registry Client — userspace subscribe/grant machinery
//!
//! Per-process client state for the CLUU registry service: register
//! outputs this process owns, subscribe to outputs owned by others,
//! and answer grant requests that mint send-only tokens for
//! subscribers.
//!
//! ## Role in CLUU
//!
//! This is the client half of the registry pattern (see
//! docs/ARCHITECTURE.md §4 "The registry pattern"). Every userspace
//! service calls `registry::init(<name>)` early in `main()` to
//! register its named outputs and obtain a control endpoint on which
//! it will receive grant requests and subscribe replies. The server
//! half is `userspace/registry/src/main.rs`. Without this module a
//! process would have to hardcode endpoint handles; with it, the
//! system rewires services by name at runtime.
//!
//! ## What it implements
//!
//! - Label constants for the registry IPC protocol:
//!   `REGISTRY_REGISTER_LABEL`, `REGISTRY_UNREGISTER_LABEL`,
//!   `REGISTRY_LIST_LABEL`, `REGISTRY_SUBSCRIBE_LABEL`,
//!   `REGISTRY_SUBSCRIBE_REPLY_LABEL`, `REGISTRY_GRANT_REQUEST_LABEL`,
//!   `REGISTRY_GRANT_DELIVER_LABEL`.
//! - `RegistryEvent` enum — decoded grant/subscribe events the
//!   process must react to on its control endpoint.
//! - `RegistryState` (private) — service name, registry endpoint
//!   token, control endpoint token, owned outputs map, lookup cache.
//! - `init` / `init_with_tokens` — bootstrap the client; `init` reads
//!   `TOKEN_REGISTRY` from the boot `ProcessInfo` page, `init_with_tokens`
//!   is used by `init` itself which creates the registry endpoint.
//! - `register_default_outputs`, `register_output`, `unregister`,
//!   `list_outputs` — producer-side API.
//! - `subscribe` — consumer-side API; returns via `RegistryEvent`.
//! - Grant-request handling — when a subscriber asks the registry for
//!   a token, the registry forwards the request to the producer's
//!   control endpoint; this module's `handle_grant_request` produces
//!   a derived send-only token via `token_derive` and replies.
//!
//! ## Design drivers & invariants
//!
//! - **§2 capability discipline:** grant requests are answered by
//!   *deriving* a restricted token from the producer's owned token
//!   via `token_derive`, not by minting a new one. The producer
//!   never escalates rights; it only narrows them.
//! - **§3 no runtime ACL:** the registry never asks "who is the
//!   caller." It merely brokers name→endpoint-token lookups. The
//!   capability token itself is the authority; the registry is a
//!   naming service, not a policy engine.
//! - **Single global per-process state** (`REGISTRY_STATE` behind a
//!   `spin::Mutex`): the registry client is process-singleton. The
//!   lock is taken briefly; no I/O happens while holding it.
//! - **Lookup cache** (`service:endpoint` → token) avoids a
//!   registry round-trip on every IPC, but cache entries are
//!   short-lived tokens — a stale cache entry fails closed at the
//!   kernel `verify_token` step, never opens an authority hole.
//!
//! ## Cross-references
//!
//! - Related files: `userspace/registry/src/main.rs` — server half;
//!   `userspace/libcluu/src/boot.rs` — `TOKEN_REGISTRY` boot token;
//!   `userspace/libcluu/src/syscall.rs` — `token_derive`, `endpoint_create`.
//! - IPC labels: see constant list above; also `REGISTRY_*` labels
//!   consumed in `userspace/registry/src/main.rs` dispatch loop.
//! - AGENTS.md: §2 (capability discipline), §3 (no runtime ACL).
//! - docs/ARCHITECTURE.md: §4 "The registry pattern".
```

This is the target quality bar. Shorter files get shorter headers;
the structure stays identical.

## 4. Findings Protocol

While documenting, the writer will discover:

1. **Contradictions** — code contradicts AGENTS.md premises, or
   contradicts other code, or contradicts docs/.
2. **Wrongly-implemented behaviors** — code does not do what its
   existing comment claims, or what its name implies, or what
   AGENTS.md says it should.
3. **Stale documentation** — existing `//!` header or `docs/` claim
   refers to removed code or renamed symbols.
4. **Dead code / unreachable branches** — file contains code that
   cannot be reached or symbols nothing imports.
5. **Race / deadlock hazards** — code looks like it would violate
   the §7 async-runtime deadlock-avoidance discipline.

### 4.1 Recording format

Every finding is recorded in `docs/DOC-FINDINGS.md` (created by this
plan) with this entry shape:

```markdown
### F-NNN — {short title}

- **File:** `path/to/file.rs:LINE` (approximate line or symbol)
- **Discovered while documenting:** `path/to/file.rs`
- **Category:** contradiction | wrong-impl | stale-doc | dead-code | race-hazard | other
- **Severity:** high | medium | low
- **Claim:** {what the doc / name / premise says}
- **Actual:** {what the code actually does, with evidence}
- **Premise violated:** §{N} (if applicable)
- **Suggested followup:** {one-line next step; NOT a fix — that's a separate task}
- **Status:** open
```

### 4.2 Inline marker

At the offending site, the writer adds a single line:

```rust
// TODO(doc-finding): see docs/DOC-FINDINGS.md F-NNN
```

The inline marker is for discoverability while reading code. The
canonical record is the central file. The writer does NOT fix the
finding — that is out of scope for this plan and would violate the
"change only what the request requires" discipline.

### 4.3 DOC-FINDINGS.md bootstrap

The file is created with a header explaining its purpose and a
table-of-contents that grows as findings are added. Numbering is
`F-001`, `F-002`, ... monotonically across the whole plan.

## 5. Execution Strategy

Three passes. Pass 1 (module skeleton), Pass 2 (file-level headers),
Pass 3 (visual capture + asset references wired into the relevant
headers).

define the architectural skeleton; their headers explain the crate as
a whole and enumerate the per-file modules underneath, so the later
file-level pass has a known target shape for each file.

1. `kernel/src/lib.rs` + `kernel/src/main.rs` (kernel root)

**Delegation policy per crate:**

- **Sisyphus directly:** kernel/, libcluu/, root-procmgr, session-procmgr, vfs. These are the architecturally load-bearing crates where a hallucinated header does real damage.
- **Delegated to a `deep` subagent (one per crate, sync):** the remaining crates. Each subagent receives:
  - AGENTS.md (full text, it's short).
  - The template (§3.1) and rules (§3.2).
  - The findings protocol (§4).
  - The crate's Pass-1 module-level headers as authoritative context.
  - Explicit instruction: "Read every file you document. Do not describe what the file should do — describe what the code actually does. Quote symbol names verbatim. If you find a contradiction, record it in `docs/DOC-FINDINGS.md` per the protocol and add the inline marker — do NOT fix the code."

- **Sisyphus reviews every delegated header** before accepting the batch. Review means: spot-check 3 files per crate against the actual code, confirm symbol names match, confirm cross-refs point at real paths, confirm premises cited actually apply.

### 5.3 Pass 3 — Visual capture + asset references

Pass 3 runs after Pass 2 so headers already exist and we only edit
the `Cross-references` section of files that gain a visual.

#### 5.3.1 Capture tooling

A new script `scripts/capture_cluu_shots.py` (Sisyphus-authored,
Python, reuses `cluu_harness` machinery) drives QEMU and captures
framebuffer snapshots. The framebuffer is **1280×720 BGRA32 =
3 686 400 bytes** (confirmed by user; this matches the existing
`QemuController.capture_fb_dump` constant exactly, so the script
reuses that dimension rather than re-deriving it). The existing
`capture_fb_dump` only fires once during cleanup; the new script
captures **multiple frames** during a live session so GIFs can be
assembled. It:

1. Boots CLUU via the same QEMU invocation the harness uses
   (reuse `QemuRun` / `HarnessConfig`).
2. Connects to the QEMU HMP monitor (reuse `Monitor`).
3. Drives the guest with `sendkey` sequences (reuse `sendkey.py`).
4. At scripted checkpoints, calls
   `monitor.pmemsave(fb_phys, 3686400, frame_NN.bin)`. The
   `fb_phys` address is taken from the serial log line
   `fb @<PHYS> <SIZE> bytes` (same regex the existing harness
   uses, `_FB_PHYS_RE` in `qemu.py`).
5. Converts raw frames → PNG via ImageMagick
   (`convert -size 1728x900 -depth 8 -colorspace sRGBA` with
   byte-order handling for BGRA32 → RGBA).
6. Stitches PNG sequences → GIF via `ffmpeg` (palette gen +
   palette use for quality) or ImageMagick
   `convert -delay N -loop 0 *.png out.gif`.

The script is a deliverable of this plan and lives in `scripts/`.
It is idempotent: re-running with the same args overwrites assets.

#### 5.3.4 Verification

- Each GIF opens in an image viewer (verified by `identify` from
  ImageMagick, or `ffprobe` for ffmpeg-produced GIFs).
- Each companion `.md` states the capture command, QEMU args,
  resolution, and what the viewer should look at.
- File headers that reference an asset are re-`cargo check`ed
  (asset paths in doc comments don't affect compilation, but the
  edit to the header itself must still parse).

### 5.4 Verification protocol

Per crate batch (Pass 1 and Pass 2):

1. `cargo check -p <crate>` (or the kernel-equivalent build path for
   kernel crates — kernel is built via `cargo xtask build`, but
   `cargo check` on the kernel lib crate works for header-only
   changes since doc comments are inert).
2. If check fails: fix the comment syntax (most common failure is
   a stray `//!` after a non-doc line, or an unbalanced Markdown
   fence) and re-run.
3. Full workspace build at the end of Pass 2: `cargo xtask build`.

Per AGENTS.md §8, evidence before assertions: the writer does not
claim "headers compile" without the `cargo check` output.

For Pass 3, verification is per §5.3.4.

### 5.5 Stopping condition

The plan is complete when:

1. Every in-scope file (320 files) has a header matching §3.1.
2. `cargo xtask build` succeeds.
3. `docs/DOC-FINDINGS.md` exists and every finding has a stable ID,
   or the file is empty (no findings) — both are valid outcomes.
4. Sisyphus has personally reviewed Pass 1 (all 48 module-level
   files) and at least 3 spot-checked files per crate in Pass 2.
5. `scripts/capture_cluu_shots.py` exists and runs.
6. `docs/assets/` exists with at least the assets that could be
   captured (broken features may be skipped with a note); every
   produced asset has a companion `.md`.
7. Every produced asset is referenced by at least one file header.

## 6. Risks and Mitigations

| Risk | Mitigation |
|---|---|
| Subagent hallucinates symbol names or behaviors | Mandatory "read every file" instruction; Sisyphus spot-checks 3 files per crate; symbol names must match codegraph/Read |
| Subagent cites a premise that doesn't apply | Sisyphus review checks each `§N` citation against the file's actual responsibility |
| Header grows too large and obscures code | Length scales with file; cap at ~200 lines for the largest files; sub-sections allowed |
| Existing technical content lost in overwrite | Writer must fold accurate existing content into the new template; review checks for lost facts |
| `cargo check` broken by malformed doc comments | Per-batch verification; fix immediately; never leave a crate red |
| Scope creep into probes/utils | Scope (§2.2) is locked; if the user wants to expand, that's a follow-up plan |
| Findings leak into fixes | Findings protocol §4.2 explicitly forbids fixing; the writer only records |
| Cross-references rot | Cross-refs verified by Sisyphus review; paths must exist on disk at the time of writing |
| Large files (root-procmgr 7837 LOC, vfs 5640) get shallow headers | The "What it implements" section MUST be broken into sub-sections by responsibility for files >1500 LOC |

## 7. Out of Scope for This Plan

- Fixing any finding recorded in `docs/DOC-FINDINGS.md`. That is a
  follow-up plan.
- Generating the comprehensive documentation suite itself. That is
  the *next* milestone; this plan produces the input material.
- Documenting probes, tests, xtask, tools, or POSIX utilities.
- Modifying non-comment code. The only allowed edits are: (a)
  replacing/extending the `//!` header block, (b) adding the inline

- Changing `AGENTS.md` or `docs/*` (except creating
  `docs/DOC-FINDINGS.md`).
